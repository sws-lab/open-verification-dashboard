# Dashboard

This repository contains a cli for comparing proof obligations in the context of formal verification. The dashboard provides an interface to compare and filter proof obligations generated by formal methods tools.

## About proof obligation format

A proof obligation is a json file with the foloiwing structure:

```json
{
  "time": "The time it took to generate the proof obligation in seconds",
  "checks": [
    {
        "kind": "safe" | "warning" | "error",
        "title": "A category for the check, e.g. 'Invalid Memory Access'",
        "message": "A message describing the check",
        "range": {
            "start": {
                "line": "The line number where the check starts",
                "column": "The column number where the check starts",
                "file": "The file where the check starts"
            },
            "end": {
                "line": "The line number where the check ends",
                "column": "The column number where the check ends",
                "file": "The file where the check ends"
            }
        },
        "callstack": "An optional object containing an unique identifier for the current context, it can be any string that helps to identify the context of the check",
    }
  ]
}
```

### Checks categories

`title` field of the `checks` array can be one of the following categories:

- `Assertion failure`
- `Invalid memory access`
- `Division by zero`
- `Integer overflow`
- `Invalid pointer comparison`
- `Invalid pointer subtraction`
- `Double free`
- `Negative array size`
- `Invalid floating point operation`
- `Stub condition`
- `Insufficient variadic arguments`
- `Insufficient format arguments`
- `Invalid type of format argument`
- `Floating-point division by zero`
- `Floating-point overflow`
- `Incorrect number of arguments`
- `Invalid shift`

If it is anything else, it will be considered as an invalid check.

## Usage

The dashboard takes two mandatory positional arguments as input for the two proof obligations to compare. If the name is `stdin` it will read the proof obligation as a single line json from standard input.

| Argument | Description |
|:--------:|:-----------:|
| `--project <path>` | The path to the project directory. Default to `pwd` |
| `--output <file>` | The file to write the json output to. Default to `stdout` where it is written in a pretty format |
| `--analyze <file>` | Filter the checks to only display the ones that are related to the file. Default to all files |
| `--exclude-not-found` | Do not include files that are not found in the project directory in the output. Default to false |
| `--filter-kind <kind,...>` | Filter conflicts by kind, comma-separated list of kinds. Default to all kinds. See [Kinds](#kinds) for the list of available kinds. |
| `--filter-error-category <category,...>` | Filter conflicts by error category, comma-separated list of categories. Default to all categories. See [Checks categories](#checks-categories) for the list of available categories. |

### Kinds

The `kind` field of the `check` object can be one of the following:

- `no_conflict_safe`: Both analyzers agree that the code is safe.
- `no_conflict_warning`: Both analyzers agree that the code is a warning.
- `no_conflict_error`: Both analyzers agree that the code is an error.
- `unchecked`: Shouldn't be in the output, it means that the check is not yet processed by the dashboard.
- `only_one_proof_obligation`: Only one proof obligation was generated by one of the analyzers.
- `safety_w1`: The first analyzer considers the code safe, but the second one considers it a warning or an error.
- `safety_w2`: The second analyzer considers the code safe, but the first one considers it a warning or an error.
- `precision_w1`: Both analyzers agree that the code is a warning. However, the first analyzer says that a sub-range is safe.
- `precision_w2`: Both analyzers agree that the code is a warning. However, the second analyzer says that a sub-range is safe.
- `error_level`: The error level is different between the two analyzers.

### Ranges

The error's ranges are dynamically computed based on the file's content. In the output file, expect the ranges to be the ones of the most imprecise tool.

## Return codes
- 0 - no conflicts found
- 1 - error in input files or arguments
- 2 - precision conflicts found
- 3  - only one tool emits a PO for a given range
- 4 - safety conflicts found
- 5 - internal error (unexpected state)
